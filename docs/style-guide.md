# Style guide

How text is written in this repository: prose, comments, file headers, citations,
error strings and commit messages. The rules here are enforced where a script can
do it (`tools/check-english.sh`, `tools/check-citations.sh`, clippy) and
otherwise by review.

## Language

- Everything is English: code, comments, documentation, CLI and firmware output,
  commit messages. `tools/check-english.sh` fails on CJK text; a line whose
  subject is CJK width may carry `i18n:allow-cjk`.
- Write for a global audience: short sentences, active voice, present tense.
  One term per concept, with the same spelling and capitalization everywhere
  (see Terminology). No idioms, humor or culturally specific references.
- Keep the subject and verb near the start of the sentence. Do not stack more
  than two nouns as modifiers of another noun.
- US spelling.

## Comments

- Comments explain *why*: the invariant, the constraint, the spec rule, the bug
  that motivated the code. The code already says *what*.
- Rust: `///` and `//!` are for users of the item (rustdoc); `//` is for the
  maintainer reading the implementation. The summary line of a `///` or `//!`
  comment is one sentence in the third person present ("Returns the ...",
  "Decodes ..."). Use `# Errors`, `# Panics`, `# Safety` and `# Examples`
  sections where they apply.
- Every `unsafe` block has a `// SAFETY:` comment directly above it that states
  in full why the block is sound and which invariant it relies on. "Same as
  above" or "ditto" is not a safety comment. Every `unsafe fn` has a `# Safety`
  section describing the caller's obligations.
- No `TODO:` / `FIXME:` markers in code. Remaining work is tracked only in
  `docs/TODO.md`; cite it (`docs/TODO.md §1.4`) if the code needs a pointer.
- No Markdown bold inside `//` or `#` comments. Bullets and code spans in `///`
  and `//!` are fine because rustdoc renders them.
- No dates, phase numbers, verification status, owner decisions or build
  instructions in comments. Dates belong to git, status to
  `docs/verification-report.md`, decisions to `docs/decisions.md`, build steps
  to `README.md` or the build script.
- Section dividers such as `// --- i32 comparisons ---` are fine in long match
  arms.

## File headers

The first line of every file states what the file is for, in one sentence.
No author, date or license lines.

| File type | Must contain | Leave out (and where it goes) |
|---|---|---|
| Rust module (`//!`) | Purpose. Design invariants a reader cannot infer, as bullets. One citation of the governing spec section. For a port `main.rs`: pin and UART assignment. | Dates and hashes (`docs/verification-report.md`), phase numbers (delete), owner decisions (`docs/decisions.md`), build steps (`README.md`, `build.sh`), byte-layout tables (move to the `///` of the `const`/`struct`), long hardware essays (shorten to the rule plus a link to the datasheet). |
| Rust test (`//!`) | What the test locks in and which failure it prevents. The governing section. | Completion criteria of past phases. |
| Generated file | Title line, then the banner `@generated by \`cargo run -p wasmicon-gen\` from \`wit/\` (...). DO NOT EDIT.` | Anything hand-written. The doc comments come from `wit/`. |
| Shell script | `#!/bin/sh`, purpose, `Requires:`, `Usage:`. | Phase references. |
| Python | Docstring: purpose, usage, notation. | Verification status. |
| WIT (`///`) | API documentation. These comments are copied verbatim into all four generated bindings, so write them for a binding user. | Decision history. |
| `Cargo.toml`, `.cargo/config.toml`, `rust-toolchain.toml`, `memory.x` | One or two lines: why the file is split out or pinned. | Repeated rationale (keep it once, in `README.md`). |
| `wasmicon.toml` | `# App manifest (docs/app-workflow.md §4.7).` plus per-board wiring notes. | Bare section numbers. |
| `ci.yml` | A file header listing the jobs and why ESP32-S3 has none. One-line comments on non-obvious steps. | Phase references. The dated runner pin stays: it is a pin. |
| `.wat`, `.ts`, `.c`, `.h` | Purpose. For app sources: which shared spec section (`apps/README.md §N`) they implement. | - |

## Citations

One form, always with the path and never wrapped in backticks:

```
docs/abi-spec.md §4.1          docs/app-workflow.md §3.9      docs/TODO.md §5-2
docs/verification-report.md §11   apps/README.md §1           docs/abi-spec.md Appendix D
docs/decisions.md D-07         docs/decisions.md A-04         docs/decisions.md P-09
```

Several sections of one document: `docs/abi-spec.md §4.1, §4.2`. Section numbers
are stable; headings may be reworded. Code never cites `docs/handoff.md`, which
is a historical record. `tools/check-citations.sh` checks that every `§` in code
names its document and that the section exists.

## Error and log strings

- Rust error messages are concise lowercase sentences without trailing
  punctuation: `unknown board \`foo\` (known boards: rp2350, esp32s3)`.
- Put values in backticks or parentheses, not in quotes: `missing export \`run\``.
- Guest log strings that a trace-equality test compares (the blink apps) are
  byte-identical across the Rust, AssemblyScript and C versions.
- Firmware strings are ASCII so that they survive `escaped()` unchanged.
- CLI usage text: `Usage:`, then one line per command, aligned with spaces.

## Commit messages

Conventional Commits, in English, imperative mood:

```
refactor(cli): translate CLI output, templates and tests to English

What changed and why, in a short paragraph.

Verified: cargo test -p wasmicon-cli, sh verify/diff-traces.sh --self-test
Not verified: ESP32-S3 build (no Xtensa toolchain on this machine)
```

Types in use: `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `ci`, `chore`.
Scopes in use: `runtime`, `gen`, `cli`, `ports`, `rp2040`, `rp2350`, `esp32s3`,
`esp32c5`, `apps`, `bindings`, `differential`, `agents`. Translation and rename
commits never change behavior; a behavior change gets its own commit. If you
proceed on an adopted default while an owner question is open, say so in the body.

## Terminology

| Use | Meaning | Avoid |
|---|---|---|
| source of truth | the file others are derived from (`wit/`, `flags.rs`) | master copy |
| normative | the document whose rules win (`docs/abi-spec.md`) | canonical, authoritative |
| generated files | output of `wasmicon-gen` | artifacts |
| role, role name | the wiring key an app looks up (`pin-by-role`) | alias, label |
| wiring, wiring table | role → GPIO mapping in `wasmicon.toml` | pinout (except for board diagrams) |
| flash (verb) | write firmware or an app to the device | burn, program |
| slot, app slot, config slot | regions in flash the loader reads | partition |
| check | what `wasmicon check` does | inspect, verify |
| verified on hardware | observed on the board | tested on real device |
| lock in | what a regression test does | pin (reserved for GPIO) |
| scaffold | what `wasmicon new` writes | template, skeleton |
| pitfall | a known trap (`P-NN`) | gotcha |
| open question | an item awaiting the owner | undecided |
| frozen decision | `D-NN` in `docs/decisions.md` | locked |
| adopted default | `A-NN` in `docs/decisions.md` | assumption |
| the owner | the person who decides | maintainer |
| host side / guest side | runtime and port / the Wasm app | native / wasm |
| supported feature set | D-07 | enabled features |
| remaining work | items in `docs/TODO.md` | backlog |
| trace | the host-call log (abi-spec §9) | log (reserved for `log` import) |
| match / identical / mismatch | results of comparing traces | agree, equal, differ |
| historical record | a document kept as written at the time | archive |
| park | what the firmware does with an empty slot | idle, wait |
| release / allocate / reserved | a handle / arena memory / pins the board keeps | free, grab, blocked |
